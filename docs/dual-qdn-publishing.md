# One Qortium dataset, two QDN destinations

The collector continues to observe Qortium only. Automatic publishing sends the
same selected DATABASE directory to Qortium `DATABASE/Network/Network` and,
when enabled, Qortal `DATABASE/xnetwork/Network`. Automatic runs still omit
SNAPSHOT; `qdn:publish:data` keeps its existing manual Qortium behavior.

## App artifacts

- `npm run build`: Qortium `dist/`, publish as `APP/Network/Network` with the
  existing `npm run qdn:publish`.
- `npm run build:qortal`: Qortal `dist-qortal/`, publish as
  `APP/xnetwork/default` with `npm run qdn:publish:qortal`.
- `npm run qdn:publish:qortal -- --dry-run` validates the Qortal build manifest
  and prints its content digest without uploading, signing or spending.

Qortal deployment hides Developers and uses lexical/window `qortalRequest`.
Qortium retains Developers and uses `qdnRequest`. The manifest records the build
network. Both show Qortium topology. These are destination-specific artifacts
from one codebase; bridge presence cannot select a network because Home exposes
both functions.

## VPS configuration

Keep the existing collector, Qortium API/account configuration, archive, payload
history and `AUTO_STATE_PATH`. Add these to the existing ignored environment file
only when the implementation and target have been approved for deployment:

```ini
QORTIUM_NETWORK_QORTAL_PUBLISH=1
QORTIUM_NETWORK_QORTAL_API_URL=https://appnode.qortal.org
QORTIUM_NETWORK_QORTAL_ACCOUNT_PATH=/path/to/existing/accounts.json
QORTIUM_NETWORK_QORTAL_ACCOUNT_ROLE=local
QORTIUM_NETWORK_QORTAL_ADDRESS=QaLdnApWW3hps1qXM8cpsL1pVgw7RtyJmN
QORTIUM_NETWORK_QORTAL_MAX_FEE=0.01
```

The account file can be a bare account record or `{ "accounts": [...] }` with
`accountAddress`, `accountPublicKey`, `accountPrivateKey`, and a matching `role`.
Use an existing private file outside published directories and git. The loader
derives the public key and address locally and rejects mismatches. `xnetwork`
must already exist and match that owner. This publisher never registers Qortal
names or sends a private signing key to a node.

Optional Qortal settings use `QORTIUM_NETWORK_QORTAL_`: `QDN_NAME` (xnetwork),
`QDN_IDENTIFIER` (Network), `DATABASE_SERVICE` (DATABASE), `API_KEY` or
`API_KEY_PATH` for a trusted authenticated node, `USER_AGENT` (curl/8.7.1), and
`UPLOAD_MODE` (zip for HTTPS remote nodes, path for loopback nodes). Non-loopback
HTTP and credentials embedded in URLs are rejected. `ACCOUNT_LOCK_PATH` can
select a shared lock location; by default it is beside the account file and
named for its public address. App and data publishing must share that lock.
Other apps using this same account must also be scheduled serially.

Every Qortal upload fetches the current ARBITRARY unit fee, checks it against the
positive configured cap and balance, and checks the account for pending
transactions. It validates the node-built transaction's public identity,
resource, reference, exact requested fee, time, group and absence of payments
before local Ed25519 signing. The public QDN content decryption key is allowed
in the normal 32-byte wire field. The wire format is checked against Qortal's
transformer and a real unsigned transaction, with the expected signature
independently generated by the established Python signer using a public test key.

## State, retries and recovery

`npm run qdn:auto-publish -- --dry-run` shows targets and selection/pending state.
It does not write a lock/state file, build a payload or contact signing nodes.

On a real run, the existing flat state is migrated without resetting the last
selected record timestamp. Invalid JSON, null, unknown versions and unrecognized
state fail closed. An exclusive run lock prevents concurrent selection. Locks
are never stolen merely because they are old: after a killed process, verify
that PID is gone and reconcile the saved receipt before removing its stale lock.

The collector payload is copied into `pending-payloads/record-*` beside the state
file. That frozen directory and its digest are reused on every retry. A changed
pending payload or changed destination is an error. No new record is selected
until the pending record reaches both destinations. This intentionally applies
backpressure: one chain can succeed independently, but new observations wait
for the lagging chain to catch up rather than dropping its queued record.

Each target persists its signature and signed public bytes **before** broadcast,
using file fsync, rename and directory fsync on Linux. Unknown results query or
resubmit that same signature. Confirmation delays and persistence failures never
restart signing. Successful targets are skipped on retry. A destination remains
pending until its transaction confirms and every expected file, including the
history, matches the local payload bytes.

Sync checks require 100% and not synchronizing. Temporary sync lag gets at most
three checks with 15s/30s backoff; other errors fail promptly. The failed target
is retained for the next scheduled run. `QORTIUM_NETWORK_MAX_ATTEMPTS` (default
5) is an alert threshold, not a discard limit. No eligible record after 26 hours
without a completed publication also raises a freshness alert and nonzero exit.
Systemd/journal monitoring must consume those failures.

Completed records retain a latest receipt in state plus per-record JSON receipts
under `publish-receipts/`. The newest frozen data is retained for review; the
previous completed frozen directory is removed after the next success. Do not
remove pending payloads or receipts to clear an error: reconcile the signature
and file mismatch first. A signed transaction that permanently expires or becomes
invalid needs operator review; automatic retries never invent a replacement.

The app helper has separate `QORTIUM_NETWORK_QORTAL_APP_STATE_PATH` (default
`target/qortal-app-state.json`) and `APP_PATH` (default `dist-qortal`). It also
persists before broadcasting, verifies every file, and refuses a different
artifact while an older publication is unresolved.

## Deployment verification

Preserve the VPS's local collector changes. Deploy reviewed publisher files and
configuration explicitly; do not reset or blindly pull the whole checkout.
Verify legacy-state dry-run first, then one scoped dual publication. Compare both
served datasets, record signatures/fees and READY status, and observe a scheduled
run before claiming automation acceptance. Offline tests simulate one-target
failure, uncertain responses, confirmation/persistence failures and recovery.
Actual Qortal Hub, Home desktop/Android, live publication and scheduled-run
results belong in release notes; fixture tests alone do not prove those gates.
